PRIORITISING CONTENT FOR FUTURE ORGANIC TRAFFIC

A time-aware analysis of search-performance signals for deciding which content should be reviewed first.
Abstract Introduction Data Methodology Results Limitations Recommendations Reproducibility Acknowledgments

Abstract

SEO teams often have more content to review than they can reasonably examine at once. This study asks whether a small set of search-performance signals can help decide which client-content pairs should be prioritised for SEO review because they are more likely to receive organic traffic in a subsequent period. Using the March 2026 FlyRank ML Internship dataset, I aggregated impressions, clicks, average position and active days from an earlier ten-day window and used whether organic sessions occurred in the following window as the binary target. A time-aware logistic regression was then compared with a simpler Week-4 baseline on a later, unseen period. On 254,121 final test rows, the model achieved a ROC-AUC of 0.9460 and Average Precision of 0.7898, compared with 0.8424 and 0.3457 for the baseline; recall was slightly lower than the baseline, but precision and F1 were higher. The model was then used to rank content and turn the scores into a practical review queue, while error analysis showed that the model can still miss pages that later receive organic sessions and can prioritise pages that do not. The result is therefore best treated as a decision-support tool: it helps narrow a large content inventory into a more useful starting point, but it does not guarantee future traffic or explain Google's ranking system.

1. Introduction / Problem Statement

SEO is partly about helping search engines understand content and helping people find it through search. But for a team managing a large content library, the practical challenge comes after that: what should we look at first? Google describes SEO as improving a site's presence in Search, while also making clear that there are no simple actions that automatically make a page rank first.

The FlyRank dataset makes this prioritisation problem visible. At the client-content level, the broader analysis produced 323,739 unique client-content pairs. Within the modelling workflow, 254,121 content pairs formed the final test set. At that scale, treating every piece of content as equally important is not a realistic review strategy. A useful system needs to narrow the list and give a team a reason to start with some content before the rest.

The signals available in the dataset provide a starting point. Search Console performance reporting includes measures such as impressions and clicks, which describe how often users saw and interacted with search results. Average position provides an aggregated view of where a result appeared.

That leads to the central question of this study:

Given a large set of content, can search-performance signals be used to identify which content should be prioritised for SEO review because it is more likely to receive organic traffic in a subsequent period?

The distinction between prioritisation and prediction is important. The purpose of this work is not to tell an SEO team exactly what will happen to a page, nor to explain why Google ranks one page above another. Google states that its ranking systems use many factors and signals across its systems. This study uses only four measurable signals from the available dataset.

Instead, the model is treated as a decision-support tool. It learns from earlier search signals, estimates the likelihood of future organic traffic, and turns a large content inventory into a ranked list for human review.

The goal is straightforward: help an SEO team decide what to investigate first, using evidence that is available before the outcome occurs, while remaining clear about what that evidence can—and cannot—tell us.

2. Data

This study uses the March 2026 release of the FlyRank ML Internship dataset, focusing on daily search-performance and organic-session records. The analysis was performed at the client-content pair level rather than at the individual daily-row level. This allowed the model to learn from the recent search activity of each piece of content and compare that activity with organic traffic observed in a later period.

The main search signals were GSC impressions, GSC clicks and average position. The modelling process used two consecutive feature/outcome windows.

3. Methodology

The modelling approach was deliberately simple. The goal was not to build the most complicated model possible, but to test whether a small set of search signals could provide a useful way to prioritise content for future SEO review.

Features

  • Total impressions: total recorded search impressions during the feature window.
  • Total clicks: total recorded clicks during the feature window.
  • Average position: mean recorded search position where a valid position was available.
  • Active days: number of days on which the client-content pair appeared in the feature data.

These features were calculated only from the period before the outcome window. No future organic-session information was used to construct them.

Target definition

A client-content pair was labelled 1 when it recorded at least one organic session during the following outcome window and 0 when it recorded none.

Model

The main model was Logistic Regression with balanced class weights. Missing values were handled through median imputation with a missing-value indicator, and numerical features were standardised before fitting.

Baseline

The Week-4 baseline used two simple search conditions: high impressions and a higher-than-threshold average position. The thresholds were calculated from the training data only. Both the baseline and the model were evaluated on the same final test set.

Validation and leakage control

The experiment preserved time order. Search signals from 1–10 March were used to predict organic sessions from 11–20 March during training. The final evaluation moved forward: 11–20 March signals were used to predict 21–31 March organic sessions.

This design prevents the model from using future outcome information when constructing earlier features. It is consistent with the general principle behind time-aware validation: time-ordered data should not be evaluated by a split that trains on future observations and tests on past observations.

Evaluation

The methods were evaluated using ROC-AUC, Average Precision, precision, recall and F1. ROC-AUC and Average Precision assess the quality of the predicted scores, while precision, recall and F1 describe performance at the selected 0.5 classification threshold.

The predicted probabilities were retained after evaluation and used to rank the final content set. This connects the model to the original decision rather than stopping at a classification table.

5. Limitations & Honest Framing

This model is useful for prioritisation, but it should not be treated as a complete explanation of future organic traffic.

First, it uses only four features: impressions, clicks, average position and active days. These give us a useful view of recent search activity, but they do not describe everything that can affect organic traffic. The analysis does not include content quality, search intent, topic, backlinks, technical SEO, seasonality, competition or changes made to the content.

Second, the target is deliberately simple. A content pair is positive when it records at least one organic session during the future window. A page receiving one session and a page receiving 100 sessions are therefore both treated as positive.

Third, the experiment uses specific March 2026 windows. The time-aware design is stronger than randomly mixing past and future observations, but this single forward evaluation does not establish that the same performance will continue across other months, clients or search environments.

The error analysis gives another useful boundary. There were 27,604 false positives and 3,699 false negatives. The model therefore both prioritises some content that does not go on to receive organic sessions and misses some content that does.

The feature coefficients also need careful interpretation. The strong coefficient for clicks does not mean clicks cause future traffic. It means clicks had the strongest estimated association with the model's prediction among the features used here.

Finally, this study does not attempt to reproduce Google's ranking system. Google describes its ranking systems as using many factors and signals across its systems. This model represents only a small subset of the information available in search.

The safest interpretation is simple: this is a prioritisation aid, not a traffic guarantee, a ranking-factor detector, or a causal model of Google Search.

6. Ranked Recommendations

The model becomes useful when its probability scores are turned into something a reviewer can act on. The final model ranked 254,121 client-content pairs according to their predicted probability of receiving at least one organic session in the subsequent period.

A high score does not automatically mean “change this page.” The underlying search signals still matter. Two pages can receive the same model probability while needing very different human decisions.

What the ranking looks like

The highest-ranked examples included both strong performers and pages with weaker positions. For example, one highly ranked pair recorded 12,790 impressions, 23 clicks and an average position of 25.20. Another recorded 5,383 impressions, 42 clicks and an average position of 2.52.

Both received a predicted probability of 1.0, but they should not receive the same treatment. The first is more naturally an investigate opportunity; the second is more naturally protect / capitalise.

This is the main reason the final output combines the model score with the underlying search signals. The ranking answers “what should I look at first?”, while the action category helps answer “what should I look for when I get there?”

The value of the model is not that it makes the SEO decision for us. It gives the next decision a better starting point.

7. Reproducibility

The computational work is maintained in the project repository. The Week 5 notebook contains the final time-aware model and baseline comparison, while the capstone notebook brings together the analysis used for the paper.

The core workflow is:

Search data → client-content features → future organic-session label → logistic regression → baseline comparison → error analysis → ranked recommendations.

The model uses the four features described in the methodology section and defines a positive outcome as at least one organic session in the subsequent window.

The experiment preserves time order. Earlier search signals are used to predict a later outcome, and the final test period is kept separate from model fitting and baseline-threshold calculation.

The project structure is:

  • work/ — assignment notebooks and capstone notebook
  • submission/paper_url.txt — the single direct URL of this deployed paper
  • paper/ — this deployed research page

The public paper does not expose client names, domains, private queries, credentials or raw exports. The identifiers shown in the analysis remain hashed.
